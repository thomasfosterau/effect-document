The CSV reader, scanner and writer are several times faster (see `vp run bench:csv`). `scanCsv` has a hand-written fast path for the common dialects (one-character separator, a wrapper escaped by doubling, no `trimWhitespace` / `lineCommentMarker` / `quoteAnywhere` / `skipRows`), with the same rows and the same errors as the grammar, which still runs for everything else. On 8 MB of mixed rows: `scanCsv` 219 → 97 ms, level with Papa Parse and ahead of d3-dsv; `read` 1.85 s → 0.34 s, 3× faster than SheetJS and ahead of d3-dsv and Papa Parse on small files; `scanCsvStream` 270 → 155 ms, faster than Papa Parse's and csv-parse's Node streams; `write` 0.9 s → 0.15 s, and `renderTable` level with d3-dsv. `read` types each row as the scanner reads it when the options allow, shares one cell per repeated value in a column (on larger texts, and only while a column's values do repeat), reads plain decimals in the scan that classifies them, (falling back to the full scan-then-type path whenever a later value contradicts a column's type, so the result is the same), column inference keeps no per-value array between its passes, and the writer renders the default options without a per-field `Result` or `Effect`. Column-count and header errors are found as before, and a stream still emits the rows before a bad one before failing on it. Fixes: a `padRows` write of a sheet with hundreds of thousands of rows no longer overflows the stack. The fast scanner reads each record into an array it reuses and copies the row out by an array literal of its width, which V8 allocates straight into the old generation once rows outlive the young one: half the garbage-collector scavenges, so `scanCsv` is ahead of uDSV's `stringArrs` and `readCsvRows` level with or ahead of its `typedArrs` on tables of numbers. The one-pass reader puts the header row before the others in place rather than copying every row into a new array (an eighth less allocation for `read`), which brings `read` on a table of numbers level with uDSV's `typedArrs`.
