# @thomasfosterau/effect-document (packages/core)

The workspace's one published package. Its core: the document schema (`src/schema`: the AST as `Schema.TaggedClass` nodes, attributes, the feature taxonomy, constructors), the profile system (`src/profile`: `defineProfile`, `Doc<F>`, conformance, `widen` / `narrow`, the built-in profiles) and the I/O pipeline (`src/io`: `Content`, `Reader` / `Writer` / `Format`, the tagged errors, `convert`), on the root entry and `./schema`, `./profile`, `./profiles`, `./io`. Each format family is a nested subpath, in a directory of its own with its tests beside the core's under `test/<format>/`: `src/csv` (`./csv`), `src/rtf` (`./rtf`), `src/ooxml` (`./ooxml`, `./ooxml/xlsx`, `./ooxml/docx`, `./ooxml/pptx`), `src/pdf` (`./pdf`, `./pdf/cos`) and `src/iwork` (`./iwork`, `./iwork/pages`, `./iwork/numbers`, `./iwork/keynote`, `./iwork/codec`). No format is on the root barrel.

## Boundary

Peers: `effect`, and `@thomasfosterau/effect-parse` as an optional peer (also a devDependency). Dependency: `fflate` (ZIP and DEFLATE). Which entry may reach which is load-bearing, because a consumer who uses no format installs no effect-parse and bundles no fflate:

- **The core** (`src/index.ts`, `src/schema`, `src/profile`, `src/io`; `.fallowrc.json` zone `core`, no outbound rule) imports no format and neither dependency. A format-specific rule (an OOXML style, a PDF font) never lives here; it goes in the format's directory, behind its own profile.
- **Each format** (zones `csv`, `rtf`, `ooxml`, `pdf`, `iwork`) imports the core by relative path, never the package's own name (which resolves to `dist/`), and never another format.
- **effect-parse** is reached only from `./csv`, `./rtf`, `./ooxml*` and `./iwork*`; **fflate** only from `./ooxml*`, `./pdf*` and `./iwork*`. `test/module-graph.test.ts` pins every entry's reach through `src/`, and `vp run check:dist` checks the built `dist/` the same way; a format that needs a new dependency changes both.

## Invariants

- **The schema is the wire format.** Every node encodes to plain JSON and decodes back (`Schema.encode` / `decode` of `Document`); a node added without its `*Encoded` interface and a place in the `Inline` / `Block` / `SheetCell` / `Shape` unions breaks that round trip. The stack-safe codec (`encodeDocument` / `decodeDocument` in `schema/codec.ts`, #191) must agree with it: a new node also gets an entry in that file's kind tables, naming its recursive fields, or deep documents of it overflow again (`test/schema/codec.test.ts` has a chain per recursive field).
- **Every node tag maps to exactly one feature** (`TAG_FEATURE` in `feature.ts`), and attribute facets are features too (`attr.id`, `attr.classes`, `attr.style`, `attr.keyValue`). A new node adds its tag there, to the right `ALL_*_FEATURES` group, to `narrow`'s handling and to `collectFeatures`.
- **`worksheetOfTrustedRows` is the one unchecked constructor** (owner decision, #227): it takes rows a reader built valid itself without checking a cell, as `trustAs` takes a document's profile. Only a reader's own typed output goes through it (the CSV reader's); anything else goes through `worksheetFromRows`, which checks every cell.
- **`Doc<F>` is a phantom brand; only `defineProfile`'s `validate` / `schema`, `narrow` and `trustAs` produce one.** `trustAs` is the unchecked escape hatch for code that built the document itself; readers use it for their own output, never for input they did not produce.
- **`narrow` never drops silently.** Every node or facet it removes or down-converts is a `LossEntry` (`dropped` or `converted`, with a `severity`, a `path` and a detail), in document order; `convert` returns the same report, and `onLoss: "fail"` turns a loss into a `ConversionError`. A lossless narrowing reports `isLossless`. Entries are plain objects with a `Schema` (`profile/loss.ts`), not class instances, because a narrowing can record one per cell; a position is a `Recorder` with a parent and a segment (`at`), and an entry's path is read up that chain only when it is recorded, so a cell's A1 address is built only for a cell that is narrowed. A new narrowing step that recurses into children passes `at(ctx, index)`.
- **The constructors skip the schema pass only for input they have checked** (`schema/trusted.ts`): `cell.text` / `number` / `boolean` / `blank`, `str`, `sheetRow`, `sheetRowFrom`, `sheetRowOf`, `sheetRowOfNumbers` (a row of plain numbers, checked by a loop that meets only arrays of doubles, so V8 never boxes them; `every` boxes each), `sparseRow`, `worksheet` and `worksheetFromRows` (its `numberRows` hint sends the listed plain rows to the same loop) build the node on its class's prototype when their guards show the struct would accept the input unchanged, and otherwise call the class constructor, so invalid input fails exactly as `new` does. A trusted node is `instanceof` its class, `Equal.equals` to the `new` one, and has the same own keys in the same order (`sparseRow` omits `height` as `new SheetRow` without one does); a new fast path keeps all three, and its test compares it against `new`.
- **A row's cells are positional** (#226, owner decision: Option A, then plain cells): the cell at array position `n` is in column `n` (a node, or a `PlainCell`: a finite number, string or boolean standing for its unstyled node, written as the bare JSON value), `undefined` is a gap (`null` in JSON, which `RowCell` and the stack-safe codec's `positions` field translate), and the last position holds a cell, so a row has one form and its width is `cells.length`. Rows stay sparse (a worksheet holds only the rows it has), but a far-right cell costs its row's width: a reader that takes untrusted input bounds positions, not cells (the XLSX reader's `maxCells`). Never build a row with array holes; `positional` fills gaps with `undefined`. Code that reads cells goes through `cellOf` / `cellAt` / `rowEntries`, which give the node for a plain cell; a plain cell and its node are the same cell but not `Equal`.
- **A worksheet row is a `SheetRow` or a plain row** (#227, owner decision): a `PlainRow` is a row's positional cells alone, standing for the `SheetRow` one past the row before it (row 0 when first) with no height, written as a bare JSON array (the stack-safe codec's `sheetRows` field). The order check runs on implied indexes, so a `SheetRow` must come after the plain rows before it. Readers emit plain rows for consecutive rows without a height (CSV always; XLSX whenever a row follows on), so a document costs no node per row. Code that reads rows goes through `rowsOf` (nodes), `rowIndexes` and `rowCellsOf` (no nodes); `rowEntries` and `cellAt` take either form. A plain row and its node are the same row but not `Equal`.
- **Errors are tagged and carried in the error channel**: `ParseError` (format, reason, optional source position, cause), `WriteError`, `ProfileViolation` (the unsupported features), `ConversionError` (a format missing its reader or writer). Their tags and field names are API: every format constructs them.

## Terms

- **Feature** — one capability a document can use: a node kind (`block.header`, `cell.date`) or an attribute facet (`attr.style`). An id is collected as its node's id facet (`attr.id.header`, #184); a profile listing `attr.id` gets every id facet, one listing a few allows ids on those nodes only. A new node with an `attr` field gets an entry in `ID_FEATURE` and passes its tag to `narrowAttr`.
- **Profile** — a named feature set with its attribute policy, the type `Doc<F>` it brands, a runtime check (`is` / `validate`) and a `Schema`.
- **Structural rule** — a limit on where an allowed feature may appear, beyond the feature set: `notWithin` (not inside a given node: RTF's `Strong` in a `Header`, #197), `onlyWithin` (only inside a given node, optionally one whose field holds one of a set of values: PPTX's `Header` in a title placeholder, #126) and `fieldValues` (the values a node's own field may hold: a PPTX `Header` at level 1). They are data (`profile/rules.ts`), not predicates, so a profile stays inspectable. The phantom `F` can't express them, so only `is` / `validate` (`collectFeaturesWithin`, `placementViolations`) and `narrow` enforce them; `narrow` handles the node as if the profile lacked the feature there, giving the rule's reason in the loss entry. The test arbitraries (`test/arbitrary.ts`) honour all three, so a property test generates only conforming documents.
- **Widen / narrow** — moving a document to a superset profile (free, by assignability) or a subset one (lossy, reported).

## CSV (`src/csv`, `./csv`)

CSV and TSV for the core's `Csv` profile: dialects (`dialect.ts`), the effect-parse grammar and the chunked streaming scanner (`scanner.ts`), the whole-text scanner's fast path (`fast.ts`) and the copy of each row it reads (`row.ts`), the reader with type inference (`reader.ts`, and `readCsvRows` beside it), plain-decimal reading (`decimal.ts`), the writer (`writer.ts`), and seeded synthetic data (`synthesize.ts`).

- **A CSV document is one `Worksheet`**, its rows plain rows (#227: each its cells alone, no node) without gaps, of plain cells (bare numbers, booleans and text) and `CellText` / `CellNumber` / `CellBoolean` / `CellBlank`, with the header row as column names: `treatFirstRowAsHeader` decides, and unset the reader sniffs it (a text first row over a column of numbers or booleans; owner decision on #88). The scanners see raw strings only, so unset means no header there. The reader never emits another node.
- **Type inference is opt-out and lossless to turn off**: `inferTypes: false` keeps every value a text cell exactly as written. It types whole columns by default (`inference: "column"`, owner decision on #88); `"cell"` is the opt-in.
- **Whole-text and streaming scans agree.** `scanCsv` and `scanCsvStream` use the same row grammar; a field, a quoted line break or a CRLF split across stream chunks parses as if it were not. A whole-text failure carries its source position; a streaming one is positioned within the unconsumed buffer, so it carries none.
- **`scanCsv` has a hand-written fast path** (`fast.ts`) for one-character separators and wrappers escaped by doubling, without `trimWhitespace`, `lineCommentMarker`, `quoteAnywhere` or `skipRows`. It must return exactly the grammar's rows, and it hands any input the grammar rejects (an unclosed quote) back to the grammar, so errors stay the grammar's. The differential test in `test/csv/csv.test.ts` ("CSV scanner fast path") compares the two on generated input across dialects; extend it with any option the fast path learns.
- **`read` has a one-pass fast path** (`fused.ts`) on top of the fast scanner, for options without `providedHeaders` or `validateHeaders` (and, for a sniffed header, with column inference): it types each row as the scanner reads it, by a guess at each column's type from its first non-null value. It gives up, and the general path (scan, then type by column, then build) runs from the start, whenever a value contradicts its column's guess, a row's width is off while widths are checked, or a quote is unclosed; so its documents and errors are the general path's. The "CSV reader fast path" test compares the two over generated tables and option sets. Its rows hold plain cells (#226): a number, boolean or text value is its bare value, a blank a `CellBlank`, so a value costs no node; a field of a column guessed to hold numbers is read from the text in place, without its string (both paths build the same forms, which the fast-path test compares). Plain decimals of up to 15 digits are read in the scan that classifies them (Clinger's fast path: exactly `Number(raw)`).
- **`readCsvRows` is `read` without the document**: the same header handling and the same typing, a value being its cell's `value` (`null` for a blank, the text for a text cell). It runs the same one-pass reader over the fast scanner (`fusedValues`), which types each field as it is read and reads a field of a number column straight from the text (`numberAt`), and otherwise the general path; the "readCsvRows" test compares it with `read` on both paths.
- **`exactNumbers: false` is the opt-in lossy mode** (owner decision, #226 thread): every value the number grammar matches is `Number` of it, its digits held or not; the fast path then keeps only the correct-rounding check (so the value still equals `Number`'s). The classifier test checks both modes against the reference.
- **Plain decimals are read exactly as `Number` reads them** (`decimal.ts`), and a number must hold its digits (a decimal a double cannot hold stays text): up to 15 digits by Clinger's fast path, and a longer one by computing its double from the digits (a quotient corrected by an exact Dekker residual, kept only within half an ulp, the ulp found by arithmetic: `ulpOf`, 0 for a power of two) and checking that it prints back as written; whatever that cannot settle within its rounding margin goes to `Number` and `String`. The classifier test ("classifies numbers as the plain-decimal grammar does") checks it against the regular-expression reference on printed doubles, nudged ones and random long digit strings.
- **The hot call sites stay monomorphic, and number rows stay doubles** (`fast.ts`, `decimal.ts`; measured on bench/csv.bench.ts). A number read in place goes through `decimalInText`, which only ever scans the source text (a scan that also meets sliced strings runs at half the speed); `readRecord` gives the string scan's slices to one call target; a record is read into a scratch array reused from row to row (after an all-number row, a scratch of doubles, stored through `storeNumber`, a store site of its own, so V8 holds its numbers unboxed: a store shared with generic rows turns them generic), then copied out by an array literal of its width (`copyRow`, with literals of their own for rows of numbers). A literal's allocation site is pretenured once its rows outlive the young generation, so no scavenge copies them; an array from `slice` has no site (bench/csv.bench.ts's floats table: half the scavenges). Keep these separations when editing the scanner, and the "copies a row of width" test, which covers every literal.
- **The grammars are compiled (`Compiler.jit`) and memoized** per dialect-and-options key, least recently used dropped at 32 entries: the whole-text grammar (`tableParser`), the streaming row grammar (`rowParser`, keyed without `skipRows`, which the stream drops before parsing). `ParserStream.parseMany` runs the compiled row grammar compiled and re-runs a failing row interpreted, so streaming errors are the interpreter's.
- **Synthesis is reproducible per seed**: the same `SynthesisSpec` with the same `seed` yields the same table (a Lehmer generator, row-major); without a seed the generator is seeded from Effect's `Random`.

## OOXML (`src/ooxml`, `./ooxml`)

Office Open XML: `src/ooxml/xlsx` (SpreadsheetML; the core `Spreadsheet` profile), `src/ooxml/docx` (WordprocessingML; its own `Docx` profile), `src/ooxml/pptx` (PresentationML; its own `Pptx` profile), over `src/ooxml/shared` (the effect-parse XML parser and writer helpers in `xml.ts`, the OPC package reader / ZIP writer in `opc.ts`, and the mapping of package failures to `ParseError` in `errors.ts`, and the grouping of list paragraphs into nested lists that the DOCX and PPTX readers share in `lists.ts`).

Each format is its own entry (`./ooxml/xlsx`, `./ooxml/docx`, `./ooxml/pptx`) and imports only `shared`, never another format, so a consumer's bundler keeps one format without the others.

- **Each format reads and writes exactly its profile.** XLSX dates are written as ISO-8601 shared strings and read back as text (no date serials or styles yet); a feature the writer cannot encode is excluded from the profile, never silently dropped at write time.
- **Packages are read through relationships, not fixed paths**: the main part is found from `_rels/.rels` (`officeDocument`), with the conventional path as the fallback; a missing part is an `OpcError` of kind `MissingPart`, surfaced as the `ParseError`'s `cause` (`ooxmlParseError` in `shared/errors.ts` maps every package failure).
- **Lists**: DOCX list paragraphs are recognised by numbering (`word/numbering.xml` decides bullet or ordered per `numId` and level; without it, `numId` 2 is the ordered list the writer emits), PPTX ones by `buChar` / `buAutoNum`; consecutive items at deeper levels nest inside the item before them. A DOCX item's blocks after its first paragraph are written indented to the item's level (`w:ind` / `w:tblInd`, the numbering level's indent), and a paragraph or table indented to an open list's level is read back into that list's last item (#195). A PPTX item's later paragraphs are written unbulleted at its level's `marL` and read back into the item; an ordered item with `buAutoNum@startAt` begins a new list (#196).
- **A PPTX heading is a slide's title** (#196): the reader takes a title placeholder's paragraphs outside lists as level-1 headers, and the writer writes a header there as plain title text, so `Pptx` allows `block.header` only at level 1, only inside a `title` / `ctrTitle` placeholder (`TITLE_PLACEHOLDER_TYPES`) and not inside a list, through its structural rules; `PptxRead` is `Pptx`.
- **A worksheet's `sheetData` is read by a fast scanner** (`parseXmlResult(xml, "sheetData")` in `shared/xml.ts`): plain names, plain attributes and text, built into the very elements the parser builds; the rest of the part is parsed by the parser with that content cut out. Anything the scanner does not recognise (a comment or CDATA anywhere before or inside it, a prefix, `xmlns`, unusual spacing, a mismatched tag) leaves the whole part to the parser, so trees and errors are the parser's. The "fast content scanner" test compares the two on generated sheets; extend it with any markup the scanner learns.
- **A worksheet's rows are read straight from `sheetData` where they can be** (`xlsx/sheetData.ts`, through `parseWithScannedContent` in `shared/xml.ts`): `<row>`s of `<c>`s holding a `<v>` or an `<is>` of plain `<t>`s go into rows with no element tree; the rest of the part is still parsed. At anything else (an `<f>`, a run, a prefixed attribute, a duplicate, a comment, a sheet over `maxCells`) the scanner gives up and the tree path reads the part, so rows and errors are the tree path's. Both paths type cells through `cellOfText` (`xlsx/cellText.ts`) and build rows with `xlsx/rows.ts`; `test/ooxml/xlsx/sheetData.test.ts` compares them on generated sheets, so extend it with any markup the scanner learns. `xlsx/xml.ts` re-exports a fixed list from `shared/xml.ts`, so the XLSX entry's surface does not grow with the shared module.
- **XLSX rows are plain where they can be** (#227): a row right after the one before it is read as a plain row, one after a gap as a `SheetRow` with its index; the writer reads both through `rowIndexes` and `rowEntries`.
- **Writers are byte-reproducible**: every ZIP entry carries the fixed `ZIP_MTIME` (1980-01-01), so the same document always writes the same bytes.

## RTF (`src/rtf`, `./rtf`)

RTF for its own `Rtf` profile (`profile.ts`): an effect-parse lexer plus a small interpreter (`reader.ts`) and a writer (`writer.ts`).

- **The lexer is total**: every input lexes, so the reader fails only on content it cannot decode, never on RTF syntax.
- **Formatting is tracked per group** (`{ … }` pushes and pops the bold / italic / underline / strike state) and turned into nested `Strong` / `Emph` / `Underline` / `Strikeout` around `Str` runs.
- **Destinations it does not model are skipped wholesale** (font and colour tables, stylesheets, info, pictures, headers and footers, list tables, and every `\*` destination); add a name to `DESTINATIONS` rather than special-casing it in the interpreter.
- **`\uN` is followed by one ANSI fallback character, which is skipped**; negative `N` is a signed 16-bit code point.
- **The writer has no semantic headings**: a `Header` is a bold, larger paragraph, and reads back as a `Para`.

## PDF (`src/pdf`, `./pdf`)

PDF for its own `Pdf` profile. Three layers: the object layer `src/pdf/cos` (the object model, a lenient lexer / parser, stream filters, `PdfFile` with xref tables and streams, object streams, incremental updates and repair, `PdfBuilder` / `rewritePdf`), text extraction `src/pdf/text` (fonts, encodings, CMaps, the content-stream interpreter, and layout inference into blocks), and the reader / writer on top.

`src/pdf/cos` imports nothing from `src/pdf/text` or the reader / writer: it is published as its own entry (`./pdf/cos`) for working with PDF structure directly.

- **The object layer is synchronous and throws its own tagged errors** (`PdfSyntaxError` with the byte offset, `PdfFilterError` with the filter, `PdfEncryptedError`); only the reader and writer turn failures into a `ParseError` / `WriteError` in the error channel.
- **Malformed input is repaired, not trusted.** A broken cross-reference chain triggers a scan of the whole file (`rebuild`), an unreadable object, object-stream member, trailer or Form XObject is skipped, and recursion is bounded (page tree depth 64, Form XObjects 12 deep, reference cycles through `/Length` guarded). Encrypted files are refused.
- **The reader prefers the tags** (#198): when the structure tree owns at least 98% of the visible text (`TREE_COVERAGE` in `text/layout.ts`), blocks come from its elements (`text/structure.ts` reads it, honouring `/RoleMap` and a custom `Heading N` type, bounded in depth and size, cycles refused); otherwise, and for untagged files, structure is inferred from the layout: the most common font size is body text, larger sizes rank as heading levels (unless the outline, `text/outline.ts`, has an item with the heading's text: its depth is the level, #20), gaps wider than the usual leading split paragraphs, a leading bullet or number makes a list item, runs of monospaced lines are code; `/ActualText` replaces the glyphs it spans.
- **OCR is injected, never bundled.** A page that paints images but has no text is OCRed only through an engine the caller supplies (`ocr` option, or the `OcrEngine` service via `PdfOcrReaderLive`); the reader hands it images as stored (JPEG / JPEG 2000 / CCITT / JBIG2 still encoded, the rest as samples) and decodes no image codec itself. Pages still without text are always listed in `meta.pagesWithoutText`, never dropped silently.
- **The writer tags its output** (#198): every piece of text it sets belongs to a marked-content sequence (`BDC` with an `/MCID`) owned by a structure element, decoration is an `/Artifact`, and the `/ParentTree` maps each page's MCIDs and each link annotation's `/StructParent` back to its element. A new block or inline the writer renders opens its element with `Typesetter.begin` / `end`.
- **The writer embeds nothing**: the standard 14 fonts with WinAnsiEncoding; a character outside it is written as `?`.
- **`PdfDict.entries` is a public native `Map`** in the object model (callers read it, iterate it in insertion order and pass their own); changing it is an API change (#155).
- **`src/pdf/text/data.ts` is generated** (base encodings, a subset of the Adobe Glyph List, the standard 14 font widths) by `scripts/generate-pdf-data.py` from the copies bundled with ReportLab; edit the script, not the file. The fixtures in `test/pdf/fixtures` record their provenance in its README.

## iWork (`src/iwork`, `./iwork`)

Read-only Apple iWork readers, each with its own profile: `keynote.ts` (slide text), `pages.ts` (body text), `numbers.ts` (sheet structure). They sit on the container codec (`./iwork/codec`): `bundle.ts` (the ZIP bundle and its `.iwa` components), `iwa.ts` (chunk framing), `snappy.ts` (the Snappy block codec), `protobuf.ts` (the wire reader), `archive.ts` (archived objects and messages), `registry.ts` (the message type ids the readers use), `text.ts` (text storages to paragraphs) and `errors.ts` (the codec's `IworkError`); `read.ts` is what the three readers share.

- **Read-only, text only.** Writing needs Apple's proprietary object-graph schemas; there is no writer, and no reader claims more structure than it extracts (Numbers has no cell values yet).
- **iWork's Snappy is block-only** (no stream framing or CRC); copies may overlap and are expanded byte by byte. The compressor emits literals only, which is valid and accepted by Apple's decoder.
- **The codec is synchronous and fails only with `IworkError`** (`errors.ts`): a `Schema.TaggedError` with a `reason` (`NotZip`, `Encrypted`, `Truncated`, `Malformed`, …) and the component, object and offset it happened at. Inner layers re-position an error as it crosses them (`rethrowing`, `shiftOffset`, `withLocation`); the readers (`read.ts`) turn it into a `ParseError` whose `cause` is the `IworkError`, or skip the component in `lenient` mode. An `.iwph` entry marks a password-protected document, which is refused.
- **Message type ids are reverse-engineered** (keynote-parser's v14.4 mapping) and may drift between iWork versions; add a new one to `registry.ts` with its archive name.
- **Fixtures are vendored** from MIT-licensed projects (`test/iwork/fixtures/ATTRIBUTION.md`); keep the attribution with any new one.
